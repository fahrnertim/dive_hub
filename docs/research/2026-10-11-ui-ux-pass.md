## Part A: Bulk Upload — how Dives are selected

### How it works today

The logbook toolbar has one button per sendable Connection, "Send to SSI…". Its dialog sends **the Dives the logbook's
list shows for the Connection's Diver**: the site, the search text and the "Show only" chips that are in the address at
that moment (`PushRun.tsx`, `SendDialog`: `list: { siteId, q, only }`). The Diver select, the sort and the page don't
count. The API also takes `{ ids: [...] }` (at most 500), which the web client never uses.

The dialog shows a sentence ("Sends the dives of Erika in this list, one at a time…"), a count, three unticked
checkboxes (also update changed Dives; also updates that remove SSI's verification; also change numbers), a "Left out"
list (held back by site, already up to date, beyond the ceiling of 100), an estimate, and "Cancel" / "Send N dives".

### Judged against the questions

| Question | Today | Evidence |
|---|---|---|
| Which Dives go? | **Not answerable.** "In this list" refers to a list behind the dialog; the filters that shape it aren't named, and the Dives aren't listed. | `32-logbook-send-dialog` |
| How many? | Yes: the count line and the button "Send N dives". | same |
| Why are some left out, before the start? | Mostly: "Left out" groups held-back Dives by site with a link. The reason reads "lack something SSI needs"; the fix (give the site its SSI ID) is one link away and not named. | same |
| Change the set without leaving? | **No.** No untick per Dive, no scope choice. Both links (the site, "Show these dives in the logbook") close the dialog and drop the ticked choices. | `PushRun.tsx` |
| Is "whatever filter is active" understandable? | **Hidden state.** A User who searched "wreck" an hour ago sends only wreck Dives and is told a number, not a reason. The opposite case too: with no filter, "Send to SSI…" means the whole logbook, which the button doesn't say. | `01-logbook`, `32` |
| Risky choices obvious? | **No.** "Also update", "also where it removes SSI's verification" and "also change numbers" look like any checkbox. Removing a dive centre's verification can't be undone from Dive Hub. On the German phone the label and its hint run together ("…geändert wurdenDas ersetzt die Werte in SSI: 1 Tauchgänge.") and the plural is wrong for 1. | `35c-logbook-send-dialog-changed-de-dark-390` |
| Dead end? | With every Dive held back the dialog says "Nothing to send with these choices." above a disabled "Send 0 dives". | `32-logbook-send-dialog` |
| Progress, stop, continue? | A strip on the logbook: progress bar "x of y", "Stop"; after the end a summary, "Continue", "Dismiss" and "Not sent (N)". Clear while you are on the logbook. | `33-logbook-run-stopped` |
| Findable afterwards? | **No.** The text says "You can leave this page", but no other page shows a run. Only the newest run is shown; the five kept runs have no list. "Dismiss" is stored in the browser (`localStorage`), so a dismissed run and its "Not sent" list are gone on that device and still there on another. | `PushRun.tsx` (`PushRunStrip`) |
| Stopped for a sign-in? | "SSI wants you to sign in again. Do it in your account." — no link, and "Continue" is offered although it fails until the sign-in is done. | `33`, `34-logbook-run-stopped-de-dark-390` |

### Options

**A1. Text and links only (S).** Name the scope in the dialog ("12 dives: at SSI test reef, search 'wreck', not in SSI",
or "your whole logbook, 214 dives"); say what a held-back Dive needs; replace the disabled "Send 0 dives" state with a
plain explanation and one action; a warning block around the two risky choices with a line break before the hint and a
correct singular; a link to the account in the sign-in stop.
Cost: about half a day, no API change. Tests: `ui-quality.spec.ts` (send dialog case gains the scope line and the
nothing-to-send state), `translations.test.ts`. Doesn't let anyone change the set.

**A2. The dialog owns the selection (M) — recommended.** Everything in A1, and:

- A **scope choice** at the top of the dialog (radio group): "The dives in the list now (12)", "Everything not in SSI
  yet (48)", "Changed since sent (3)". The first is the default when a filter is on, the second when none is.
- A **list of the Dives that will go**, collapsed behind "Show the 12 dives", each row date · site · number with a
  checkbox to leave it out, and "Select all / none". Unticking sends `ids` instead of the list. Above 100 rows the
  list shows the first 100 and says so (the ceiling is 100 anyway).
- Held-back Dives stay in "Left out", each with its reason and what fixes it.

```text
┌ Send to SSI ───────────────────────────── ✕ ┐
│ Which dives of Erika?                        │
│ (•) The dives in the list now          12    │
│     at SSI test reef · not in SSI            │
│ ( ) Everything not in SSI yet          48    │
│ ( ) Changed since sent                  3    │
│                                              │
│ ▸ Show the 12 dives                          │
│   ☑ Jan 15, 2026 · SSI test reef · #43       │
│   ☐ Jan 14, 2026 · SSI test reef · #42       │
│                                              │
│ ⚠ These change what is already in SSI        │
│ ☐ Also update 1 dive changed since sent      │
│   Replaces SSI's values.                     │
│ ☐ … also where SSI's verification is lost    │
│ ☐ Also change dive numbers in SSI            │
│                                              │
│ Left out (2)                                 │
│   2 at Blue Hole: the site needs SSI's ID →  │
│ About 1 minute.                              │
│                      [Cancel] [Send 11 dives]│
└──────────────────────────────────────────────┘
```

Cost: 2–3 days. The preview route already answers counts; it needs to return the Dives to send (first 100: id, date,
site, number) — a small API addition, so [clients.md](../spec/clients.md) changes in the same slice. No schema change,
no change to ADR 0047's rules (ADR 0047 itself left `ids` open for this). Works on a phone as it is one column;
checkboxes are native React Aria ones, so keyboard and screen reader come with them.
Tests: `push-run.spec.ts` (new: a Dive unticked in the dialog isn't sent; scope "everything not in SSI" ignores the
logbook's search), server test for the preview's list, `ui-quality.spec.ts` (dialog states at 320 px, en and de),
`translations.test.ts`.

**A3. Checkboxes on the logbook's rows (L).** A checkbox per row, a sticky bar "3 selected · Send to SSI… · Clear",
"Select all 214 matching". Familiar from mail clients. Against it: ADR 0047 lists it as considered and "owner: not
now", so it needs a new ADR; rows are whole-row links today, so each gets a second target; a page holds 25 Dives, so
"all matching" is a second kind of selection to explain; at 320 px the row loses a column of width; the sticky bar
competes with the phone's bottom navigation. Cost: about a week, with a new ADR. Tests: nearly all of
`push-run.spec.ts`, the logbook cases in `ui-quality.spec.ts`, keyboard order.

**Recommendation: A2.** It answers "which Dives" where the User is asked to confirm, needs no new ADR, and keeps the
logbook rows as they are. A3 only pays off once a second bulk action exists (bulk delete, bulk site).

**Runs findable (separate, M), recommended with either option:** a run in progress shows in the navigation (a small
progress mark beside "Logbook", with the count announced) so "you can leave this page" is true; the strip's ended
state gains "Earlier runs" listing the kept five (date, sent, not sent, state), each opening its "Not sent" list;
"Dismiss" is stored with the run on the server, not in the browser. This needs one field and a route, so clients.md
changes. Tests: `push-run.spec.ts`, `ui-quality.spec.ts`.

## Part B: Certifications — how and where

### Who looks, and when

- **The Diver, at a dive centre's counter:** "show me your card". Wants the picture, big, in two taps on a phone.
- **The Diver or a parent, before a trip:** which cards do we have, is anything expiring.
- **The User who keeps a logbook for someone else:** enters a new card after a course.
- **A guide checking a buddy's level: not possible and not proposed.** ADR 0028 and ADR 0050 keep cards to the Users
  who manage the Diver. It stays a Visibility question for later.

### Today

A quiet text button "Certifications", one of four or five on each Diver's row of the Divers page, opens a dialog
(`04f-divers-certifications`). Nothing on the page says whether a Diver has cards. ADR 0050 decided "a Certifications
section of the Diver page"; a dialog was built because there is no page per Diver.

The card list itself:

| Check | Today | Evidence |
|---|---|---|
| Sorting | The API's order, newest issue date first; no control. Fine for a handful of cards. | `04f` |
| Expired cards | An "Expires" date among the facts, same weight as the rest; an expired card looks like a valid one. | `Certifications.tsx` |
| Imported vs typed | A badge per card (self-declared / card seen / verified with agency). Clear. An imported card's "Edit" opens a form with only notes, which surprises. | `04f` |
| Picture | Inline at the bottom of the card when stored. **Not confirmed in the capture:** `04f` shows no picture on the imported cards, only a small mark under the facts. Check in the build slice whether the fake serves one and at what size it renders. No way to see it large. | `04f` |
| Empty state | Text plus "Add certification" and "Import from SSI". Good. | `ui-quality.spec.ts` case |
| "Import from SSI" | One button per Connection of that Diver, beside "Add certification" at the same weight. Fine with one Connection. | `04f` |
| Import report | A success notice with counts and the named leftovers, dismissible. Good. | `Certifications.tsx` |
| Closing | **No Close button**; only Esc or a tap on the 16 px rim around the dialog on a phone. | `10c-divers-certifications-de-phone` |
| Form on a phone | 13 fields in a scrolling modal, Save at the very end. | `10d-divers-certification-form-de-phone` |

### Placements compared

| | Discoverable | Phone width | Privacy line | Cost |
|---|---|---|---|---|
| **1. As now: dialog from the Diver's row** | Poor: a text button among five, no sign that cards exist | A modal inside a long page; no close control | Said in the dialog | none |
| **2. A Certifications section with the Diver** (inline on the Divers page, as there is no Diver page) | Good: a summary line is always visible where the Diver is | One column; tiles stack; no modal for the list | Said once in the section | M, no ADR (it is what ADR 0050 decided) |
| **3. Profile drop-down or account page** | Best for one's own cards, **none** for a kept Diver's (a child's cards aren't "my account") | Fine | Clear for own cards | S for a link; a section on the account page contradicts ADR 0050 ("no strip … on the account page now") and needs a new ADR |
| **4. Card tiles with picture, level, agency, expiry; summary on the Divers page** | Good | Tiles need about 280 px, so one per row on a phone | As 2 | Part of 2; alone it is a restyle of the dialog |
| **5. A hint on the Dive page** ("deeper than your Open Water limit") | It would be seen, but it is a new feature: it needs a level's meaning (the Agency catalog ADR 0050 left out) | — | A Dive page is seen by buddies' Users too: the hint would have to be hidden from them | L, new ADR; not now |

### Recommendation: 2 with 4, plus the link from 3

- The Diver's row gets a **Certifications line**: count, the newest card, and a badge when one expires within 90
  days or is expired. No cards: "No certifications yet · Add".
- The line opens the section **in place** (a Disclosure, its open state in the address so a link can point at it):
  card tiles with picture thumbnail, agency and level, number, issued, expiry, verification badge. Expired cards go
  last, greyed, with "Expired" in words. The thumbnail opens the picture large (the counter case).
- "Add certification" is the section's one main action; "Import from SSI" sits beside it as the quiet one. The form
  stays a dialog, with a Close button and its actions kept in view.
- The profile menu gains **"My certifications"**, a link to the own Diver's open section. A link only: no second
  place that holds cards, so ADR 0050 stands.
- Not now: Dive-page hints, visibility to guides, expiry reminders by mail.

```text
Logbooks you keep
┌──────────────────────────────────────────────────────────────┐
│ (Er) Erika (you)   3 dives     Codes  Body weight  Rename     │
│ ▾ Certifications   3 cards · Advanced Adventurer (SSI)        │
│                    [1 expires Dec 2026]                       │
│   Only you and the Users who keep this Diver see these.       │
│   ┌────────────────────┐ ┌────────────────────┐              │
│   │ [picture]          │ │ [picture]          │              │
│   │ SSI Advanced Adv.  │ │ SSI Open Water     │              │
│   │ Verified with SSI  │ │ Verified with SSI  │              │
│   │ No. 1234567        │ │ No. 7654321        │              │
│   │ Issued Jun 2024    │ │ Issued May 2023    │              │
│   │ Edit notes  Delete…│ │ Edit notes  Delete…│              │
│   └────────────────────┘ └────────────────────┘              │
│   ┌────────────────────┐                                     │
│   │ (no picture)       │   [+ Add certification]             │
│   │ DAN First Aid      │   Import from SSI                   │
│   │ Self-declared      │                                     │
│   │ Expires Dec 2026 ⚠ │                                     │
```

Cost: 2–3 days. The Divers list needs a count, the newest card and the nearest expiry per Diver (a small API addition
for managing Users only, so clients.md changes). Tests: `certifications.spec.ts` (the section instead of the dialog;
new: an expired card is marked and sorted last; the picture opens large; the profile link lands on the open section),
`ui-quality.spec.ts` ("Divers, a diver's certifications…" case, plus the expired state and 320 px), a server test for
the summary, `translations.test.ts`. ADR 0050 gains an "As built" line; no new ADR.
