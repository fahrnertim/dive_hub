# SSI (MySSI) app API as a Target, and as a Source

Question from the project owner (2026-10-04): community projects have reverse-engineered SSI's undocumented app
API. Can Dive Hub use them for its first Target, instead of (or as well as) the QR payload planned in the
[spec](../spec/README.md) and [scenario 4](../spec/data-model.md#4-dive-pushed-to-ssi-then-changed)?

Method: public information only. I read the published projects' code and docs and ran none of it. I didn't sign
in to SSI, send any requests with credentials, or create an account. Claims that only a real account can settle are
marked [?] and listed under [Checks for the owner](#checks-for-the-owner).

Markers:
- **[V]**: I checked it against the primary source myself (repository contents and dates, licence files, store listings, SSI's own pages).
- **[S]**: reported by a project's author, often "verified against a real logbook", but not checked by me.
- **[?]**: not verified, inferred, or the sources disagree.

## Summary

- **What exists.** Five open-source projects and two closed-source iOS apps talk to SSI's private JSON API at
  `api.divessi.com/app/a21.php`, and two more projects drive the web logbook at `my.divessi.com`. All of the
  open-source projects but one (2023) appeared in 2026. All are MIT or Apache-2.0 except one GPL-3 browser extension. The best documented is [divesend][divesend], with a 1,500-line API
  reference (MIT, 2026-09). The most recent working evidence is [divebridge][divebridge-l], verified against a real
  logbook on **2026-10-01** [S].
- **Does it still work?** Probably yes. SSI's relaunched app is version 5.0.43 (2026-10-01) [V][appstore], but every
  community client still sends a 4.1.x version string. divebridge created and read back dives on 2026-10-01 [S].
  ssi-dive-map's weekly read job succeeded every week up to 2026-09-28 [V][dive-map-runs]. Whether the 5.x app itself
  still uses this endpoint is unknown [?].
- **Sign-in:** e-mail and password, sent as query parameters of a GET, are exchanged for a token. There's no OAuth,
  no refresh token, no 2FA or captcha and no app secret in any project [S]. The token's lifetime isn't documented [?].
- **Writing:** one call (`save_divelog`) creates or updates a dive, including the full depth profile, temperature,
  tank pressure, GF, gas, site, buddies, conditions and computer identity. It returns the SSI dive ID [S].
  Deleting is an update that sets `deleted` [S]. The dive shows as **unconfirmed**, the same as a dive typed into the
  app or added by QR [S].
- **Reading:** the whole logbook (dives with profiles, the sites used, buddies, stats), certifications (`get_ccards`),
  gear and profile data [S]. SSI's whole site list is an unauthenticated zip file: 24,304 sites with positions
  (2026-08-15). It has **no licence** [S].
- **Risks:** no published terms, partner programme or rate limits. The password goes in a URL. Sources disagree on
  whether API-made dives break the app's logbook list [?]. SSI can switch the API off without notice.
- **Recommendation:** use the API as the default Target mode and the QR payload as the fallback. This depends on
  three things: the owner's checks with a real account, a decision on what to store (it changes "no stored
  credentials" in the spec), and an e-mail to SSI asking for partner access.

### Ratings (as in `docs/references`)

**divesend** (MIT)
- *What it is:* the API reference: endpoints, the full dive record, profile sample format, gotchas.
- *Take:* the knowledge. Its TypeScript payload code (`@divesend/core`: schema, transformer, enum tables) is
  MIT-compatible with Apache-2.0 if we keep the notice. Writing our own mapping from its reference is cleaner.
- *Don't take:* the examples in its reference contain a real third party's name, birth date, phone and city, and a
  dive centre. Never copy them into fixtures. Its enum tables say they were extracted from SSI's APK (SSI's copyright).

**divebridge (LustigePerson)** (MIT)
- *What it is:* the freshest evidence: a create → read-back → compare loop against a real logbook, plus quirks found that way.
- *Take:* the read-back verification idea and the list of quirks (units, rounding, flags). A small Python codebase; nothing to reuse directly.
- *Don't take:* its bundled `divelog_vars.json`. Fetch the lists at runtime instead (they're SSI's data).

**divessi-log-importer** (MIT)
- *What it is:* the original TypeScript client and the types for the read response.
- *Take:* the types are a useful starting point. The Suunto converter overlaps our own FIT/Suunto plans.
- *Don't take:* `samples/ssi/*.json` look like real logbook exports; don't reuse them as fixtures.

**DiveBridge (kenthejr)** (Apache-2.0)
- *What it is:* the only documentation of the web logbook path and its SSO login.
- *Take:* knowledge only, as the fallback path if the app API closes. Same licence as ours.
- *Note:* on the web form, a dive without a site **saves nothing but still answers "success"** [S].

**divessi-export, ssi-dive-map** (MIT): confirm the read path; nothing to take beyond that.

**divessi-shearwater-log-importer** (GPL-3.0): knowledge only. Its code can't go into an Apache-2.0 image.

**QR generators**: knowledge only. The keys are already in the owner's `qr-format.md`.

## 2. Authentication

**App API** [S] (the five open-source app-API projects agree):
- `GET a21.php?what=authenticate&l=<e-mail>&p=<password>` plus four fixed query parameters: a client label for
  the Android app, the app version string, language and a context flag. The answer always has HTTP status 200. It is
  `{authenticated: true, token, mid, authenticated_email, …}` or `{authenticated: false, error_message}`
  ([agrippa login.ts][agrippa-login], [divesend reference][divesend-ref]).
- Every later call sends `token=<token>` as a query parameter. Writes POST `json_data=<the record as a JSON string>`.
- `mid` is the account's **user master ID**: the SSI person/account identifier.
- **Not found anywhere:** OAuth, refresh tokens, device binding, 2FA, captcha, request signing, certificate pinning [S][?].
  Kenthejr's notes guessed the app doesn't pin certificates, and divesend's MITM captures confirm that [S].
- **Token lifetime: unknown.**
  - divesend says "hours" and caches tokens for only 5 minutes on its server ([tokenCache.ts][divesend-cache]).
  - divessi-log-importer keeps the token in a cookie for up to 400 days and never signs in again ([session.server.ts][agrippa-session]).
  - divebridge signs in again after any error.
  - None of them measured it [?].
- **Password in the URL.** The password and token travel in query strings, so any HTTP log, proxy or error message that
  prints URLs leaks them. divebridge silences its HTTP client's logging for this reason [V][divebridge-client].
- **No CORS headers**, so a browser can't call the API directly. The calls must come from our server [S][divesend-notes].

**Web logbook (fallback)** [S][kenthejr-ssi]: `POST rest.divessi.com/sso/login` with JSON
`{auth: "Portal", username, password}`, then a second login for the logbook. A `PHPSESSID` cookie then authorizes the
form POSTs, with no CSRF token. A cookie lives as long as a browser session.

**What Dive Hub would have to store per User** (for its SSI Connection):

| Option | Stored | Unattended pushes | Who does it |
|---|---|---|---|
| A. Token only | token (encrypted) + SSI account ID | until the token expires, then the User signs in again | divessi-log-importer, DiveDrop (device) |
| B. Password | e-mail + password, encrypted with a key held outside the database | always | divesend's server ([crypto.ts][divesend-crypto]: AES-256-GCM, key in a server secret) |
| C. Nothing | — | no; the User signs in for each sending session | divesend "guest" mode |

**App secret?** None. The fixed parameters are a public client label and a version string that all the projects copy
from the app's traffic. No key, signature or certificate is involved [V] (read in the five open-source app-API clients). So an open-source image
embeds no secret. It does, though, present itself to SSI as the Android app with a version number of our choosing,
which is a question of honesty and of breaking when SSI changes things. The open question is whether we also send an
honest User-Agent (decision 5).

## 3. Writing dives (broadcast)

### Create, update, delete [S]

- `save_divelog` with `odin_user_log_id: null` **creates** a dive. With an existing ID it **updates**. The answer is
  `{ok: "added to Log", odin_user_log_id: 27497631}` (or `"updated"`, with `"sql_success": "INSERT"|"UPDATE"`)
  ([divesend reference][divesend-ref], used in [diveSyncEngine.ts][divesend-sync]). divebridge and
  divessi-log-importer ignore the answer and find the dive again by reading back.
- **Delete** is an update with `odin_user_log_deleted: 1` (answer `"ok": "deleted"`). Deleted dives disappear from `get_divelog` [S].
  divesend notices dives deleted in SSI by their ID vanishing from the logbook ([reconcile.ts][divesend-reconcile]).
- The client must send the **whole record**: 342 keys, unused ones `null`. An update re-sends the server's record with
  changes on top, so fields edited in the app survive [S].
- The client picks the **SSI dive number** (`odin_user_log_nr`, highest + 1). It's the SSI logbook's own sequence,
  not the computer's dive number [S].

### How it looks in the app [S]

- **Unconfirmed**, like dives typed into the app or added by QR. Sending `confirmed`/`verified: true` is ignored.
  These come only from a dive-centre confirmation [S][divesend-ref][divebridge-readme].
- With `divecomputer_imported: true` the app shows a computer icon and a "dive computer" field [S].
- Badges marked "DC confirmation required" probably don't count unconfirmed dives [S][?].
- **Conflict:** divesend saw the logbook list go blank after tapping an API-made dive in app 4.1.272, and listed this
  as a known risk. divebridge (2026-10-01) reports dives showing fine after a refresh [S]. The 5.0.43 release notes fix
  "Empty logbook when a dive site has no dives" [V][appstore]. Needs a check on the owner's phone [?].
- The app caches the logbook: pull to refresh after a push [S].

### API or QR: which is the default

The API wins on everything except risk and credentials. It has the profile, gas and tank, buddies and computer;
updates and deletes; the ID coming back (so a Push can become `confirmed` and later `outdated` → update in place);
and no phone step per dive. The QR payload needs no account data in Dive Hub, can't be blocked, and suits Users who
won't hand over credentials.
→ **API as the default** for Users with an SSI Connection. **QR as the fallback**: without a Connection, or when the
API fails. The QR builder is small, so keep it.

## 4. Reading

### Dive sites

- **Bulk:** `GET api.divessi.com/app/APP_CACHE_SITES.zip` needs **no sign-in**. It holds a single `sites.json`,
  ~2.5 MB zipped and ~19 MB unzipped. On 2026-08-15 it had 24,304 "locked" (position-checked) sites out of 36,424,
  from 145 countries, each with ID, name, alias names, lat/lon, country ISO code, water type, current statistics and
  wildlife IDs [S][divesend-ref].
  - Two projects download it once and search it locally ([sites.py][divebridge-sites]: by name, or nearest within 5 km).
  - SSI's marketing says "65,000+ dive sites" [S][scubanews]. The difference is unexplained [?].
- The `comment` field holds moderation notes **with submitters' IP addresses** [S]. That's personal data; never store it.
- **Paged:** `get_divesites_global&last_sync=<ts>&offset&limit=10000` looks like an incremental feed, but was only
  seen returning empty [S]. A User's own logbook includes the sites they've dived (`logbook_sites`).
- **Web:** `dive_site.json.sd.php?minlat&minlng&maxlat&maxlng` returns markers in a box, with a session [S][kenthejr-ssi].
- **Rate limits:** none documented or reported [?].
- **Terms:** none published (see [§5](#5-legal-and-operational-risk)), and the file has no licence. Unlike ODbL
  (OSM, [ADR 0021](../decisions/0021-site-external-ids-and-import.md)), nothing *permits* reuse.
  - SSI is HEAD Watersports GmbH in Germany [V][imprint]. A site list built with substantial investment is
    protected by the EU database right, which forbids extracting or re-using a substantial part
    ([Directive 96/9/EC][db-directive], *Directmedia* [directmedia]).
  - Copying the file into our site table, or seeding sites from it, is therefore out.
  - Two uses look defensible, though a lawyer hasn't confirmed either [?]:
    - looking up a *single* site's ID for one Dive, live or from a per-User cache, the way SSI's own app does;
    - the User's own `logbook_sites`.
  - **Matching** our Dive sites to SSI IDs (nearest within 200 m plus name, suggested for the User to confirm)
    fits the "reference" kind of External ID in ADR 0021: we keep only the ID, never SSI's name or position.

### Buddies

- SSI keeps a **per-account buddy list** (`logbook_buddies` in `get_divelog`, and `get_buddies`). Each entry has
  [S][divesend-ref][agrippa-dives]:
  - `id`: the entry, which belongs to one account;
  - `master_id` and `buddy_master_id`: the buddy's own SSI account, when the buddy is an SSI user;
  - name, birth date, e-mail, phone, city, country;
  - `leader_nr`: the buddy's SSI pro number, if any;
  - `confirmed`, `favorite`.
- A dive's `odin_user_log_buddy_ids` lists **entry IDs from that list**. It holds no free text and no global person IDs [S].
- **Reading** both the list and the buddies on each dive works [S].
- **Adding** a buddy through the API was never captured; no `save_buddy` call is known [S]. To send a buddy, the User
  first adds them in the app, and we map our Diver to that entry. The web form also offers only the account's existing
  buddies [S][kenthejr-ssi].
- **Person identifiers at SSI:**
  - the account / user master ID (`mid`), which is also in QR codes and dive URLs;
  - the pro number (`leader_nr`, "instructor number");
  - certification card IDs (`ccard_uid`, e.g. `<centre>N<digits>-<country>`, also printed on the card and used in
    `my.divessi.com/cert/<uid>` [S]).

  I found no evidence that SSI has a separate "member number" for non-pro divers [?]. The app's buddy QR code isn't
  documented; the dive QR carries `user_master_id` [S][ssi-qr].
- For comparison, PADI: a recreational "diver number" belongs to each certification and can differ between PADI
  regions; only pros get one lasting number [S][padi-numbers].

### The User's own dives and certifications (SSI as a Source; note only)

`get_divelog` returns every dive with its profile (`diveSamples`) in one answer (no paging), and `get_ccards`
returns certifications (course, issue date, instructor and centre numbers, card ID) [S]. Together they would allow an
**import from SSI** (Dives with Recordings keyed `(ssi, odin_user_log_id)`, and Certifications). Such an import must
recognize dives that Dive Hub pushed itself, by the remote ID on the Push, or a round trip creates duplicates. Not designed here.

## 5. Legal and operational risk

- **Terms of use:** none published that I could find.
  - divessi.com links only a privacy policy and an imprint. `/terms`, `/terms-of-use`, `/agb` and similar URLs redirect
    to "page not found" [V][privacy][imprint].
  - The privacy policy says nothing about automated access, third-party apps or reuse of site data [V][privacy].
  - The app's store listing names HEAD Watersports GmbH as seller [V][appstore].
  - In-app terms shown when signing up can only be read with an account [?].
- **What that means:** no clause allows it, and none forbids it that we can see.
  - Reading your own data is backed by the GDPR right of access and portability.
  - Writing dives on a User's behalf, with their credentials, is the same act as typing them in. Every project
    describes it as "at your own risk".
  - The site file is the clearest legal limit (database right, above).
- **If SSI changes or blocks the API:** Pushes fail, the Push shows `failed` with the reason, and the User can fall
  back to QR.
  - Dives already in SSI stay there. We keep their IDs, so nothing is lost on our side.
  - A broken sign-in looks like "authenticated: false". We must tell "wrong password" apart from "API changed".
  - Precedent: Garmin's unofficial `garth` client died when Garmin changed its sign-in on 2026-03-27
    ([dive data sources](2026-10-02-dive-data-sources.md)).
  - SSI's app relaunch (5.0, 2026-08) didn't break the old endpoint as of 2026-10-01 [S]. Any 5.x update could.
- **Rate limits and User-Agent:** none documented or reported [?].
  - `get_divelog` returns the whole logbook with profiles in one answer. For a logbook of hundreds of dives that's
    megabytes, so read it once per sending session, not once per Dive.
  - The browser extension waits 1.5 s between dives "to avoid rate limiting" [S][phranx]. Send one request at a
    time, with a pause.
  - The clients send no special User-Agent [V].
- **Official partner API:** none public.
  - Partner syncs exist (Mares, Shearwater, Suunto app, Aqualung, and SCUBAPRO LogTRAK) [S][ssi-news].
  - LogTRAK links accounts with a "Connect SSI Account" step in the partner app that the user confirms in MySSI
    [V][logtrak]. So SSI has an account-linking mechanism for partners. It's undocumented, and there's no
    application page.
  - SSI says Garmin switched off its side ("no longer offers an interface for … diving") [S][garmin-ssi].
  - Whether an individual or an open-source project can apply: unknown. The only way to find out is to ask SSI [?].

## 6. Data model fit

What the API forces, and proposals for [data-model.md](../spec/data-model.md). These are text for the owner to
decide on (see [decisions](#decisions-for-the-owner)); the spec is unchanged.

### Where SSI and PADI identifiers go

| Identifier | What it identifies | Goes on |
|---|---|---|
| SSI user master ID (`mid`, `buddy_master_id`, QR `user_master_id`) | a person's SSI account | **Diver** → External ID `(ssi, mid)` |
| PADI account (sign-in at padi.com) | a person's PADI account | **Diver** → External ID `(padi, …)`, if ever needed |
| SSI buddy entry `id` | one row in *one* SSI account's buddy list | **Connection** (a per-Connection mapping Diver ↔ entry), not the Diver |
| SSI certification card ID (`ccard_uid`), PADI diver number | one certification | **Certification**.number (exists) |
| SSI pro number (`leader_nr`), PADI pro number | a professional's standing with the agency | **Membership**.number (exists) |
| SSI dive ID (`odin_user_log_id`) and SSI dive number (`odin_user_log_nr`) | a Dive's copy at the Target | **Push** (remote ID exists; add the remote number) |
| SSI site ID | a place | Dive site External ID `ssi` (exists, ADR 0021) |
| SSI dive centre ID (`facility_id`) | a dive centre | **Operator** → External ID `(ssi, …)`, later |

### Proposed text

**Diver** (add):
> *External IDs:* `(Diver, Source, external id)`. Unique per Source among Divers that aren't merged; a Diver has at most
> one per Source. It records the Diver's account at a service (SSI user master ID, PADI account). Certification and
> membership numbers are not External IDs; they stay on Certification and Membership. Setting an SSI ID that another
> Diver already has proposes linking the two Divers (as in scenario 2's claim), and doesn't create a second Diver.

**Connection** (extend):
> *Connection* — User, Source or Target type, configuration, the account ID at the service (for SSI the user master ID,
> which also becomes the External ID of the User's own Diver), the stored secret (see the credentials decision) and when it
> was last used successfully, state (`active`, `needs sign-in`, `failed`). *Diver mappings:* `(Connection, Diver,
> remote id)` for Targets whose people are per-account records, such as SSI's buddy list; set by the User when pushing a
> Dive with that Diver as Participant, or matched by `buddy_master_id` = the Diver's SSI External ID.

**Push** (extend):
> *Push* — … mode (`QR payload`, `API`, `browser automation`), state, **remote ID** (SSI dive ID) and **remote number**
> (the Target's own dive number, which differs from the Dive's number), **remote reference** (a stable value we send,
> e.g. as SSI's dive-computer dive reference, for finding the dive again when the answer was lost), pushed snapshot,
> **read-back result** (fields the Target stored differently).
> A Push in mode `API` that gets an ID back is `confirmed`. "Confirmed" means delivered; it is not SSI's dive-centre
> confirmation, which Dive Hub can't set. When it becomes `outdated`, re-pushing **updates the same remote dive** (a new
> Push with the same remote ID). Deleting the Dive offers to delete it at the Target too.

**Scenario 4** (rewrite step 3 for the API):
> 3. With an API Connection, re-pushing updates the SSI dive in place (P2 has P1's remote ID; P1 stays in the history).
> With a QR Push, SSI can't be updated, and the current warning stays.
> 4. Deleting D1 asks whether to delete it in SSI too (an update with `deleted`). If not, the reminder stays.

**Other things the API forces:**
- **Time:** SSI stores local wall-clock time without a zone, to the minute. Push: our UTC + offset → local. Import
  from SSI: the offset comes from the site's time zone or the User (cross-cutting rule A8).
- **Vocabulary:** SSI's condition IDs map to our words in the Target adapter code, as device values do
  ([ADR 0015](../decisions/0015-overrides-vocabulary-and-browser-tests.md)). The lists are fetched from SSI, not bundled.
- **Samples:** resampled to 5 s on push. Our Sample series has everything SSI takes (depth, temperature, NDL, tank pressure).
- **Site required in practice:** a Push needs the Dive site's SSI ID (as in scenario 4). Without one, Dive Hub asks the
  User to pick from nearby SSI sites, or to type the ID.
- **Glossary:** "confirmed" needs a note, since SSI uses the word for dive-centre verification.

## 7. Recommendation

1. **Both. The API first, with QR as the fallback**, but only after the owner's checks below and decisions 1–3.
   If SSI answers with a partner route, prefer that.
2. **The credentials decision.** I suggest **option A** to start: store the token encrypted, plus the SSI account ID,
   and never the password. When the token expires, the Connection shows "needs sign-in". Then measure how long tokens
   last. Move to option B (encrypted password, key from an environment secret) only if tokens turn out to last hours
   and the User opts in. The spec's "no stored credentials" changes to "no stored passwords" (A) or "passwords only
   encrypted, on request" (B). This needs an ADR, plus a line in the [client contract](../spec/clients.md) (the
   client must show what is stored and offer "disconnect").
3. **First slice:**
   - an SSI Connection (sign in, store the token, show the SSI account);
   - "Send to SSI" on one Dive: pick or confirm the SSI site ID (from the User's `logbook_sites`, nearby suggestions,
     or typed), check for an existing SSI dive at the same time (±2 min), create with summary and profile, store
     remote ID and number, read back and show differences;
   - `outdated` → update in place;
   - delete offers deletion in SSI;
   - no buddies, gear or photos yet;
   - no bulk site download;
   - an HTTP client that never logs URLs.
4. **Second slice:** the QR payload for Users without a Connection, then buddies (Connection Diver mappings).
   Importing from SSI as a Source comes later.

### Checks for the owner

All of these need your own SSI account and phone:

1. **Terms:** in MySSI 5.0.43, open the legal pages and the terms shown at sign-up. Look for clauses on automated
   access, third-party apps, reuse of content and the site list. Note the app version.
2. **Test dive by API:** send one throwaway dive from a script on your machine (for example with divebridge's CLI, which
   has a dry run that shows the payload first). Then, in the 5.x app (pull to refresh), check:
   - it's listed as unconfirmed;
   - the dive view opens, the profile chart renders, and **the logbook list doesn't go blank**;
   - site, computer and notes are right.
3. **Update and delete it**, and check that the app follows both.
4. **Answer:** does the create answer contain `odin_user_log_id`?
5. **Token lifetime:** note the time of sign-in, then retry `get_divelog` with the same token after 1 h, 1 day and 1 week.
6. **Side effects:** after an API sign-in, is the phone app still signed in (single session)? Does SSI send a
   "new sign-in" e-mail? Is 2FA offered in the account settings?
7. **Surface interval:** set it on the test dive and see whether SSI shows it as seconds or minutes.
8. **Ask SSI** (support / partner contact) whether a self-hosted, open-source logbook can get partner access, like
   LogTRAK's "Connect SSI Account".

## Decisions for the owner

1. **API as a Target mode at all**, given no terms, no partner programme and "may break any time"? (Recommended: yes,
   after checks 1–4, with QR kept as the fallback.)
2. **Credentials:** A (token only), B (encrypted password) or C (nothing stored)? This changes "no stored credentials"
   in the spec and needs an ADR. (Recommended: A.)
3. **Write to SSI** asking about partner access before building? (Recommended: yes, in parallel.)
4. **SSI site data:** only look up single sites and the User's own sites, never seed or store SSI's list.
   (Recommended: yes. The data is protected by the database right and has no licence.)
5. **Identify honestly:** send a `User-Agent: DiveHub/<version> (+repo URL)` next to the app parameters, accepting
   that SSI could block it? (Recommended: yes.)
6. **Model:** Diver External IDs, Connection Diver mappings, and Push remote number / reference / read-back as proposed in [§6](#6-data-model-fit).
7. **Scenario 4:** an `outdated` Push updates in place through the API, and deleting a Dive offers deletion in SSI.
8. **Order:** the API slice first, QR second (or QR first, as the smaller, credential-free step)?
9. **Reuse code?** divesend's MIT payload code with its notice, or our own implementation from the reference.
   (Recommended: our own, using the reference and divebridge's read-back quirks as test cases.)

## Decided (2026-10-04)

The owner decided, recorded in [ADR 0024](../decisions/0024-ssi-target-via-app-api.md):
1. Use the API as a Target mode: yes.
2. Credentials: the **User chooses at connect** between "Keep me signed in" (encrypted password; only offered when the
   operator sets an encryption key) and "Don't store my password" (token only). The second choice says up front that
   the token may expire.
3. No request to SSI for partner access for now.
4. SSI site data: an **admin import like OSM**, which goes further than recommended above. The admin confirms that
   SSI's list has no licence and that importing is the operator's risk. Moderation comments (IP addresses) are never stored.
5. Honest User-Agent: yes.
6. Model changes as proposed in §6: accepted and written into the [data model](../spec/data-model.md) and the
   [glossary](../glossary.md).
7. Scenario 4: update in place, deletion offered. Accepted.
8. The API slice comes first.
9. Our own implementation, with no code taken from the projects.
