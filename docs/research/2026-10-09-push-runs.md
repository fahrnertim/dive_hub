# Push runs: research, answers and implementation plan (slice 22c)

Decided in [ADR 0047](../decisions/0047-push-runs.md) (proposed until the owner accepts it). This note holds what
the ADR rests on and how to build it.

## How SSI and others send many dives

Asked by the owner (2026-10-09) before choosing a pause and a ceiling. Public pages and code only, read by a research
subagent; nothing was run against SSI. Markers as in the [SSI reference](../references/ssi-app-api.md): **[V]** read
in code or docs, **[S]** reported and not verified, **[?]** not found.

- **No batch call [?].** No `save_divelogs`, no array in `json_data`, no sync endpoint is documented anywhere. Every
  client that writes sends one `save_divelog` per dive.
- **SSI's own app.** How it uploads a dive computer's download is not known [?]. Our own capture (the reference, "SSI's
  app: its sync") shows about 12 requests within a second when the app opens, and a second logbook pull within about a
  minute refused. The save answer's `temp_id` "mirrors `odin_user_log_nr` on write; local-sync artifact"
  ([divesend's API reference][divesend-ref] [V]); the same document calls the Android app local-first with a
  background sync [S]. That points to a local queue, nothing more.
- **divesend** ([`syncAllDives`][divesend-sync] [V]): a plain loop, one dive after another, no sleep, no batch size,
  no retry, no ceiling. It reads the logbook once before the run, skips dives already linked, collects failures and
  goes on. Dives must be sorted oldest first because it counts SSI's dive number up itself.
- **divebridge (LustigePerson)** ([client.py at 7b24e90][divebridge-l] [V]): one POST per dive; signs in again and
  retries once on an API error; no delay. Its README describes a dry run first, duplicate detection and a read-back.
- **kenthejr/DiveBridge** ([notes][divebridge-k] [V]): the older form endpoint, one dive per POST; lists a
  `get_divelog` read-back for duplicates as open. No notes on limits.
- **Limits seen [?].** No report of HTTP 429 or 403, a blocked account or address, or a captcha on `api.divessi.com`.
  No terms-of-use wording on automated access found. No report of anyone sending hundreds of dives. The only refusal on
  record is the pull's "wait until". Absence of reports is weak evidence: the projects are small.
- **Official bulk paths.** Dive computer sync into the app, and SCUBAPRO LogTRAK's "Share with SSI" for chosen dives
  ([SSI blog][logtrak] [V], no limits stated). QR is one dive per code. SSI's Garmin beta import is said to be
  discontinued ([Garmin forum][garmin-forum] [S]). No file import on my.divessi.com found [?].

**What it means here.** Any pause is already more careful than the known clients. The ceiling and the stop rule are
insurance against what nobody has tried. Dive Hub differs from them in one way that could matter: it reads the logbook
back after every save (to compare what SSI stored), and logbook pulls are the one thing SSI is known to throttle for
its app. Single sends 2 s apart have not been refused so far. The first real runs are the test; the reference has the
owner's check for it.

## The owner's answers (2026-10-09)

| Question | Answer |
|---|---|
| Which Dives | The logbook's list (Diver, search, site, "Show only"); the API also takes Dive ids. No row checkboxes. |
| Updates | Opt-in per run, off by default; updates that remove a verification are a second opt-in. |
| A Dive that can't go (blocking requirement, `exists`) | Skip and report; `exists` is decided on the Dive's page. Only a Connection problem or two failures in a row stop the run. |
| Pacing | 5 s pause, 100 Dives per run for SSI, declared by the adapter. Chosen after the research above. |
| Order | Oldest first stays (the SSI adapter numbers "highest plus one"). The owner asked whether highest first would avoid clashes if dives are renumbered one day: that concerns a renumbering pass, which is not designed (ADR 0047, "Renumbering"). |

| Renumbering | Its own slice and ADR, built before Push runs (22b; Push runs become 22c): [ADR 0048](../decisions/0048-dive-numbers.md). See the next section. |

Settled without asking, in the ADR: the worker with one job per Dive, polling for progress, cancel and continue, the
last five runs kept, MCP unchanged, slice 22c.

## Dive numbers first (slice 22b)

The owner's idea (2026-10-09): a Dive has the number its Source gave and a number Dive Hub computes; a Provider's
numbers can optionally be made to follow Dive Hub's, with a tick when sending.

**Designed the same day: [ADR 0048](../decisions/0048-dive-numbers.md)**, with the findings in the code, the owner's
answers, the SSI checks and the implementation plan in [Dive numbers](2026-10-09-dive-numbers.md). In short: the
number is computed (place by start time plus the Diver's "dives before this logbook", apnea by a Diver's setting) and
never typed; the choice is a setting on the Connection, not a tick per send; Dive Hub never gives a dive a number
another dive at the Provider has. What a Push run gains from it is in ADR 0047 (marked "ADR 0048") and in the plan
below (marked "22b").

What was open here and where it went:

| Open on 2026-10-09 | Settled in ADR 0048 |
|---|---|
| What the computed number is; what counts; typed or Source's number | "What the number is" |
| The number stays out of "changed since sent" | "'Number differs' and 'Set number'" |
| What a Provider declares | "What a Provider declares" (`numbers`) |
| What the slice offers before Push runs | "The choice", and "Set number" on a Dive's page |
| A clash at the Provider | "A number another dive there has" |
| Dives that are only at the Provider | the same section: they keep their numbers, the client points to the import |
| The three owner's checks at SSI | The build's first step ([checks](2026-10-09-dive-numbers.md#owners-checks-the-builds-first-step)) |

## Implementation plan

**Not before slice 22b (dive numbers, [ADR 0048](../decisions/0048-dive-numbers.md)) is built.** What that ADR adds
to a run is worked in below and marked "22b"; it builds on what slice 22b leaves: `pushes.setNumber`, a status's
`current.number`, the capability `numbers` and the Connection's `diveNumbers.follow`
([plan](2026-10-09-dive-numbers.md#implementation-plan)).

For a session on Sonnet. Every design choice is in ADR 0047 or here; if something is missing, stop and ask the owner
instead of deciding. Tests first, one at a time (red, then green), in the order below.

### Seams the tests sit at
1. **The HTTP API** (`app.inject` on `createTestApp`, as `apps/server/test/provider-layer.test.ts` does), with the
   fake SSI (`test/fake-ssi.ts`) and the ledger (`test/fake-ledger-provider.ts`). Results are read through the API
   (`GET /api/push-runs/{id}`, `GET /api/dives/{id}/providers/{provider}`), not from tables.
2. **The worker's step**, called as the worker calls it: `ctx.providers.pushRuns.step(runId)`, in a helper
   `runToEnd(runId)` that calls it until it returns `null`. No Graphile runner in tests (as `imports.processImport`).
3. **The classification** as a pure function (`push-run-plan.ts`), for the table in the ADR.
4. **The browser** (`apps/web/e2e`), at the User's level.

### Server: modules
- `apps/server/src/providers/provider.ts`: `Capabilities.limits.run: { pauseMs: number; maxDives: number } | null`.
  SSI `{ pauseMs: 5000, maxDives: 100 }`; the ledger `{ pauseMs: 1000, maxDives: 3 }` (a small ceiling keeps the tests
  short); the hand-over adapter `null`. The capabilities view in `routes.ts` passes it on.
- `apps/server/src/dives/list-filter.ts` (new): the conditions `listScope` in `apps/server/src/routes.ts` builds for
  `siteId`, `q` and `only` (with `notAtProvider`, `NO_RECORDING`, `FINDINGS_SHOWN`), moved out as
  `diveListFilter({ userId, diverIds, siteId, q, only })` returning `{ base, filters, where }`. `listScope` uses it;
  `GET /api/dives` answers exactly as before (`dive-list.test.ts`, `dive-list-rows.test.ts` stay green untouched).
- `apps/server/src/providers/push-run-plan.ts` (new, pure): `planItem(status, options)` where `status` is what
  `pushes.status` returns for one Dive and Provider, and `options` is `{ updates, updatesRemovingVerification,
  canUpdate }`. Returns `{ send: 'create' | 'update' }` or `{ leftOut: 'up_to_date' | 'requirements_unmet' |
  'update_not_chosen' | 'removes_verification' | 'update_unsupported' }`. Order of the checks: a blocking `unmet` →
  `requirements_unmet`; no `current` → `create`; `current.upToDate` → `up_to_date`; no `update` operation →
  `update_unsupported`; not `updates` → `update_not_chosen`; `current.updateRemovesVerification` and not
  `updatesRemovingVerification` → `removes_verification`; else `update`.
  - **22b:** `options` gains `numbers`. Where the checks above end in `up_to_date`, `update_not_chosen` or
    `update_unsupported`, and `current.number?.differs && current.number.canSet`: not `numbers` → the left-out
    reason it had, counted as `numberNotChosen` as well; `current.number.removesVerification` and not
    `updatesRemovingVerification` → `removes_verification`; else `{ send: 'number', wanted, held: current.remoteNumber }`.
    An `update` needs nothing more: `pushes.send` carries the number, and `current.updateRemovesVerification` already
    counts a number change (slice 22b).
  - **22b:** `orderItems(items, heldNumbers)` (pure, same file): the `number` items first, in the order ADR 0047 gives
    ("Order"). `heldNumbers` is the number of every current remote dive of the Connection's Diver at this Provider, by
    Dive. Repeatedly take, among the `number` items whose `wanted` no other Dive holds, the one with the highest
    `wanted`, and move that Dive's held number to `wanted`; the `number` items left when none can go are left out as
    `number_taken`. Then creates and updates by start time, then id. The ceiling cuts this list from the front.
- `apps/server/src/providers/push-run-service.ts` (new): `createPushRunService({ db, registry, connections, pushes })`
  with
  - `preview(userId, connectionId, request)` and `start(userId, connectionId, request)`: both resolve the Dives
    (the list filter for the Connection's Diver, or the ids; only Dives of that Diver, not deleted, of a Diver the User
    manages; ordered by `starts_at`, then `id`), run `planItem` on each via `pushes.status`, and cut the Dives to send
    at `maxDives`. `start` inserts the run and its items and queues the first step in one transaction
    (`graphile_worker.add_job('push_run_step', json_build_object('runId', …), job_key => 'push-run:' || id,
    max_attempts => 1)`), then deletes that Connection's finished runs beyond the newest five.
  - `get(userId, runId)`, `list(userId)`, `cancel(userId, runId)`, `continue(userId, runId)` (queues a step as `start` does).
  - `step(runId): Promise<{ afterMs: number } | null>`: one Dive, as the ADR's table "What stops a run" says. `null`
    when the run ended or isn't active. It takes its item with one conditional statement (`UPDATE push_run_item SET
    state = 'sending' … WHERE state = 'waiting' … RETURNING`, the lowest `position`), plans it again with `planItem`
    (the Dive may have changed), calls `pushes.send(userId, diveId, provider)`, or for a `number` item
    `pushes.setNumber(userId, diveId, provider)` (22b; `provider_number_taken` and `provider_number_nothing_to_set`
    are skips with the reasons `number_taken` and `up_to_date`, not failures), and writes the item. It never throws:
    an unexpected error is the item's `internal_error` and counts as a failure. `afterMs` is the adapter's
    `limits.run.pauseMs`.
  - `requeueActive()`: for every run `queued` or `running`, items in `sending` become `waiting` and a step is queued.
  - The run's Connection is loaded by `connection.user_id = userId`; anything else is not found.
- `apps/server/src/providers/layer.ts`: builds it, returns `pushRuns`.
- `apps/server/src/providers/push-run-routes.ts` (new; `routes.ts` is long enough): the six routes of the ADR, TypeBox
  schemas, registered where the provider routes are. Status codes: 202 for start and continue; 409 for
  `push_run_active`, `push_run_nothing_to_send`, `push_run_not_active`, `push_run_not_stopped`; 404 for
  `push_run_not_found` and a foreign Connection (as the other Connection routes answer). The new codes join the
  problem-code list and its translations.
- `apps/server/src/worker.ts`: task `push_run_step`: `const next = await pushRuns.step(runId); if (next) await
  helpers.addJob('push_run_step', { runId }, { runAt: new Date(Date.now() + next.afterMs), jobKey: 'push-run:' + runId,
  maxAttempts: 1 })`. `await pushRuns.requeueActive()` before `run(...)`, beside `siteImports.failInterrupted()`.
  `startWorker` gets the service from `main.ts`.

### Server: data (one migration, generated with drizzle-kit, reviewed, committed; never `push`)
- `push_run_status`: `queued`, `running`, `done`, `cancelled`, `stopped`.
- `push_run`: `id`, `user_id` (→ user, cascade), `connection_id` (→ connection, cascade), `provider` text, `diver_id`
  (→ diver), `status` (default `queued`), `updates` boolean, `updates_removing_verification` boolean, `numbers` boolean (22b), `left_out` jsonb
  (`{ upToDate, requirementsUnmet, updateNotChosen, removesVerification, updateUnsupported, beyondCeiling, notFound }`,
  with 22b also `numberNotChosen` and `numberTaken`;
  the counts at the start), `consecutive_failures` integer default 0, `stop_code` text null, `cancel_requested_at`,
  `created_at`, `started_at`, `finished_at`. Unique partial index `push_run_one_active_uq` on `connection_id` where
  `status in ('queued', 'running')` (a unique violation is `push_run_active`). Index on (`user_id`, `created_at`).
- `push_run_item_state`: `waiting`, `sending`, `sent`, `skipped`, `failed`.
- `push_run_item`: `run_id` (→ push_run, cascade), `dive_id` (→ dive, cascade), `position` integer, `action` text
  (`create` | `update` | `number` (22b), as planned), `state` (default `waiting`), `outcome` text null (`created` |
  `updated` | `linked` | `numbered` (22b)), `reason` text null (a skip reason: `exists`, `requirements_unmet`,
  `up_to_date`, `update_not_chosen`, `removes_verification`, `dive_not_found`, `number_taken` (22b); or the problem
  code of a failure), `push_id` (→ push, set null),
  `attempts` integer default 0, `finished_at`. Primary key (`run_id`, `dive_id`); index (`run_id`, `position`).
- The account export and deletion (ADR 0044): runs are not exported (they are a log of Pushes, which are); check that
  deleting a User or a Connection takes them along (the cascades) and add the tables wherever `account.test.ts` lists them.

### Views
- **Run:** `id`, `connectionId`, `provider`, `diverId`, `status`, `stopCode`, `updates`,
  `updatesRemovingVerification`, `numbers` (22b), `cancelRequested` (boolean), `counts: { total, waiting, sent, skipped, failed }`,
  `leftOut` (the counts above), `pauseMs`, `createdAt`, `startedAt`, `finishedAt`. With `GET /api/push-runs/{id}` also
  `items: [{ diveId, position, action, state, outcome, reason, dive: { number, startsAt, siteName } }]`.
- **Preview:** `provider`, `diverId`, `limits: { pauseMs, maxDives }`, `counts: { create, update,
  updateRemovingVerification, upToDate, requirementsUnmet, updateUnsupported, notFound }` (what is there, whatever the
  options say; with 22b also `number`: dives already there whose number differs and can be set, whether or not they
  are also updated; `numberRemovingVerification`: those of them that need the second update choice; `numberTaken`:
  those that can't be ordered; all three 0 where the Connection doesn't follow numbers), `send` (how many a start with these options queues), `beyondCeiling`, `withLeftOut` (Dives to send
  that an advisory requirement sends without someone), `estimatedSeconds` (`send × (pauseMs / 1000 + 4)`),
  `blocked: { total, dives: [{ diveId, number, startsAt, siteId, siteName, unmet }] }` (the first 100, oldest first).

### Server tests, in this order (`apps/server/test/push-runs.test.ts`, plus `push-run-plan.test.ts` for the pure part)
1. `planItem`: one case per row of the ADR's table "What is sent" and per check above.
2. The capabilities carry `limits.run`; a start at the hand-over Provider answers `provider_unsupported`
   (`provider-layer.test.ts` expects `run: null` in its capabilities).
3. The preview counts from Dive Hub's data and calls no Provider (the fake saw no call).
4. A start answers 202; stepping to the end sends each Dive once, oldest first; the run is `done`; each Dive's status
   shows it at the Provider.
5. A Dive with a blocking requirement unmet is in `blocked` and not in the run; the others go.
6. Changed Dives go only with `updates`; one whose update removes a verification only with both options (fake SSI;
   `dive-verification-codes.test.ts` shows how such a Dive is set up).
7. A dive at the same time already at SSI: the item is `skipped` with `exists`, nothing is saved there.
8. The ceiling: with more Dives than `maxDives`, the oldest go and `beyondCeiling` says the rest; a second run takes them.
9. A second start on the Connection answers `push_run_active` with the first's `runId`; another Connection's run starts.
10. `step` answers `afterMs` equal to the Provider's run pause.
11. The Provider down (the ledger's `down`): the second failure in a row stops the run with `provider_unavailable`,
    the rest still `waiting`; back up and continued, it ends `done` and the failed ones were tried again.
12. Tokens expired and nothing renews them: the run stops at once with `provider_sign_in_needed`, the item `waiting`;
    after signing in, continue finishes it.
13. Cancel between two steps: the run is `cancelled`, the rest `waiting`; a step after that does nothing. Cancel of a
    finished run answers `push_run_not_active`.
14. A crash: an item left `sending`, then `requeueActive`, then stepping: the run ends, and SSI has one dive for that
    Dive, not two (the answer of the first save was lost; it is found by our reference and linked).
15. `provider_busy` on an item (the Dive's lease is held): it waits and goes on a later step; after three it is `failed`.
16. Scoping: another User gets 404 for the Connection and the run; ids of another User's Dives are counted `notFound`
    and never sent; a deleted Dive likewise.
17. The sixth run of a Connection deletes its oldest.
18. `provider-contract.ts`: an adapter with `delivery: handed_over` and `limits.run` not null fails the suite.

22b, against the ledger with the Connection following numbers (`provider-numbers.test.ts` shows the set-up):

19. `planItem`: an up-to-date Dive whose number differs is `number` only with `numbers`; with a Provider that says a
    number change removes a verification, only with `updatesRemovingVerification` too; with the Connection not
    following (`current.number` null), never.
20. `orderItems`: numbers moving up come out highest first, numbers moving down lowest first; two Dives that swap
    numbers are left out as `number_taken`; creates and updates follow, oldest first.
21. A run's creates carry the Dives' numbers (the ledger has them), with nothing ticked.
22. An older Dive added here after three were sent: the preview counts `number: 3` and `create: 1`; a run with
    `numbers` sets the three from the highest down, then creates the new one with its own number; every number at the
    ledger then equals the Dive's. Without `numbers` only the create goes, numbered the ledger's own way, and the
    run's `leftOut.numberNotChosen` is 3.
23. A number held by a dive only at the ledger: that item is `skipped` with `number_taken`, the run goes on.
24. A changed Dive whose number differs, with `updates` and `numbers`: one item (`update`), one save at the ledger,
    values and number both there.

### Client duties for clients.md
A new section "Sending many Dives to a Provider" after "Sending a Dive to a Provider (SSI)", and `limits.run` where
the capabilities are described:
- Offer it only for a Connection whose Provider has `limits.run`.
- **Must preview first** and show: how many go; how many are held back by a requirement and which (lead to the fix, as
  for a single send); how many are beyond the ceiling; how many go without a Participant; the Provider's notices; the
  time it takes.
- **Must leave both update choices unticked**, say that an update replaces the Provider's values, and say that the
  second removes a verification.
- **22b: must leave `numbers` unticked** and offer it only when the preview's `counts.number` is above 0; say how many
  dives get a new number there and that a number change can need the second update choice
  (`numberRemovingVerification`). An item's action `number` and the reason `number_taken` get their own words.
- **Must show progress** as a count of the total while `queued` or `running` (poll `GET /api/push-runs/{id}`, no
  faster than every 2 s), find a run again after a restart of the client (`GET /api/push-runs`), and offer to stop it.
- **Must show the result**: every item not `sent` with its reason, leading to the Dive; `exists` means the question is
  asked on the Dive's page.
- **Must show why a run stopped** (`stopCode`, a `provider_*` code, with the Provider named), how to fix it, and offer
  continue. Must not time the message out.
- `push_run_active` names the run that is going: show that one instead of an error.
- The order of items is the server's; show `position`, don't rely on it being by date.
